## 학습 목표

- 컨테이너와 가상 머신의 차이를 **커널 공유·격리 기술(namespace, cgroup, UnionFS)** 관점에서 설명합니다.
- 이미지·컨테이너·저장소(registry)의 관계와 레이어 구조를 그림으로 설명합니다.
- `docker run/ps/exec/start/stop/rm/images/rmi/logs/stats` 등 핵심 명령으로 컨테이너의 수명 주기를 관리합니다.
- `Dockerfile`과 `docker commit`으로 이미지를 만들고, 장치(`--device`)·볼륨(`-v`)·GUI(X11)·네트워크(`--network=host`)를 연결합니다.
- ROS 2 Humble 컨테이너를 직접 구성해 보고, MentorPi의 `mentorpi` 컨테이너를 안전하게 다루는 규칙을 지킵니다.

## 왜 Docker인가

B03에서 본 것처럼 MentorPi의 모든 기능 프로그램은 호스트(라즈베리파이 OS, Debian)가 아니라 **Docker 컨테이너(Ubuntu 22.04 + ROS 2 Humble)** 안에 있습니다. 이렇게 하면

- 호스트 OS 버전과 무관하게 ROS 2가 요구하는 **정확한 환경**을 재현할 수 있고,
- 설치가 꼬여도 컨테이너를 바꾸면 되며(호스트는 깨끗하게 유지),
- 같은 이미지를 여러 로봇에 배포할 수 있습니다.

"내 컴퓨터에서는 되는데요"라는 문제를 없애는 것이 Docker의 핵심 가치입니다.

### Docker란

Docker는 Go 언어로 작성된 오픈 소스(Apache 2.0) **애플리케이션 컨테이너 엔진**입니다. 리눅스 커널의 기능으로 프로세스를 격리합니다.

| 커널 기능 | 역할 |
|---|---|
| **namespace** | 프로세스가 보는 세계를 분리: PID(프로세스 번호), 네트워크, 마운트(파일 시스템), 사용자, 호스트 이름 |
| **cgroup** | CPU·메모리 등 자원 사용량 제한·측정 |
| **UnionFS**(overlay) | 읽기 전용 레이어 여러 장을 겹쳐 하나의 파일 시스템처럼 보이게 함 |

즉 **컨테이너의 정체는 격리된 프로세스**입니다. 별도 OS를 부팅하지 않으므로 밀리초~초 단위로 시작합니다.

### 가상 머신과 비교

| 항목 | 가상 머신(VM) | 컨테이너 |
|---|---|---|
| 격리 단위 | 하드웨어를 흉내 내고 **게스트 OS 전체**를 실행 | 호스트 **커널을 공유**, 프로세스만 격리 |
| 시작 시간 | 수십 초~수 분 | 밀리초~초 |
| 크기 | 수 GB(OS 포함) | 수십 MB~수 GB(커널 제외) |
| 격리 강도 | 강함(클라우드의 사용자 간 격리) | 상대적으로 약함(앱 간 격리) |
| 다른 OS 커널 | 가능(Windows 위 Linux) | 불가(리눅스 컨테이너는 리눅스 커널 필요) |

라즈베리파이처럼 자원이 적은 장치에서 ROS 2 환경을 통째로 넣기에 컨테이너가 알맞은 이유입니다.

### 구조: 클라이언트-서버

`docker` 명령(클라이언트)은 요청만 보내고, 실제 일은 **Docker 데몬(dockerd)**이 합니다. 둘은 UNIX 소켓(`/var/run/docker.sock`)이나 네트워크로 REST API를 주고받습니다. 이미지는 **레지스트리(registry, 예: Docker Hub)**에서 내려받습니다.

| 명령 | 흐름 |
|---|---|
| `docker build` | Dockerfile → 데몬이 레이어를 쌓아 **이미지** 생성 |
| `docker pull` | 데몬이 레지스트리에서 이미지를 내려받아 로컬에 저장 |
| `docker run` | 이미지로 **컨테이너** 생성·시작(로컬에 없으면 먼저 pull) |

## 세 가지 핵심 개념

@fig[b10-layers] 이미지는 읽기 전용 레이어의 묶음이고, 컨테이너는 그 위에 쓰기 가능한 레이어 한 장을 얹은 실행 인스턴스입니다. 지워지면 안 되는 데이터는 볼륨으로 호스트에 둡니다.

### 이미지(image) — 특수한 파일 시스템

- 프로그램·라이브러리·설정과 실행 준비 정보(환경 변수, 기본 명령 등)를 담은 **읽기 전용 루트 파일 시스템**
- 여러 **레이어**가 겹쳐 있음. 앞 레이어는 뒤 레이어의 바탕이고, 한 번 만든 레이어는 바뀌지 않음
- 뒤 레이어에서 파일을 지우면 실제로는 "삭제 표시"만 됨 → 이미지 크기는 줄지 않음. 그래서 **불필요한 파일은 같은 레이어 안에서 지워야** 합니다.
- 같은 바탕 레이어는 여러 이미지가 **공유**(디스크·다운로드 절약)

### 컨테이너(container) — 이미지의 실행 실체

- 이미지와 컨테이너의 관계는 **클래스와 인스턴스**와 같습니다(B06). 하나의 이미지로 여러 컨테이너를 만들 수 있음
- 생성·시작·정지·일시정지·삭제가 가능한 격리된 프로세스
- 이미지 위에 **쓰기 가능한 컨테이너 레이어**가 얹힘. 컨테이너를 **삭제하면 이 레이어도 사라짐**
- 모범 사례: 컨테이너 레이어에는 데이터를 쓰지 않고(stateless), 남겨야 할 데이터는 **볼륨이나 호스트 디렉터리**에 씀

### 저장소(repository)와 레지스트리

- 레지스트리(예: Docker Hub) 안에 여러 저장소가 있고, 저장소 안에 **태그(tag)**별 이미지가 있음
- 이름 형식 `저장소:태그` — 예: `ros:humble`, `debian:latest`. 태그를 생략하면 **`latest`**

## 설치와 hello-world

MentorPi 이미지에는 Docker가 이미 설치되어 있습니다. 아래는 새 라즈베리파이(Debian)에 설치할 때의 공식 절차 요약입니다.

```bash
sudo apt-get update
sudo apt-get install ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/debian $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo groupadd docker                  # (이미 있으면 메시지만 나옴)
sudo gpasswd -a $USER docker          # sudo 없이 docker 명령 사용
sudo reboot
docker version
docker run hello-world                # "Hello from Docker!" 가 나오면 성공
```

`docker run hello-world`는 로컬에 이미지가 없으면 자동으로 내려받고(pull), 컨테이너를 만들어 실행한 뒤 메시지를 출력하고 끝납니다. 이어서

```bash
docker images                  # REPOSITORY, TAG, IMAGE ID, CREATED, SIZE
docker inspect hello-world     # 이미지 상세 정보(JSON)
```

```text
docker run [OPTIONS] IMAGE [COMMAND] [ARG...]
```

| 옵션 | 의미 | 로봇 예 |
|---|---|---|
| `--name 이름` | 컨테이너 이름 | `--name humble` |
| `-it` | 대화형 + 터미널(함께 사용) | 셸 사용 |

| `--rm` | 종료 시 자동 삭제 | 일회성 실험 |
| `-p 호스트:컨테이너` / `-P` | 포트 매핑 / 임의 포트 | 웹 영상 스트림 |
| `--network=host` | 호스트 네트워크를 그대로 사용 | **ROS 2 DDS 통신** |
| `--device=/dev/video0` | 특정 장치 전달 | 카메라 |
| `-v 호스트경로:컨테이너경로` | 볼륨(바인드 마운트) | `-v /dev:/dev`, 공유 폴더 |
| `-e 이름=값` | 환경 변수 | `-e DISPLAY=$DISPLAY` |
| `--restart=always` | 재부팅·종료 시 자동 재시작 | 로봇 부팅 시 자동 기동 |

```bash
docker pull debian
docker run -it debian /bin/bash       # 프롬프트가 root@<컨테이너ID> 로 바뀜 → 컨테이너 안
exit                                  # 셸 종료 → 이 컨테이너는 정지
```

### 목록·진입·종료

```bash
docker ps            # 실행 중인 컨테이너
docker ps -a         # 정지된 것 포함 전부   (-l 최근 1개, -n 3 최근 3개, -q ID만)
```

| 방법 | 동작 | 나올 때 |
|---|---|---|
| `docker attach <ID>` | 컨테이너의 **시작 프로세스**(PID 1) 터미널에 붙음 | `exit`하면 PID 1이 끝나 **컨테이너가 정지** |
| `docker exec -it <ID> /bin/bash` | 컨테이너 안에 **새 셸 프로세스**를 띄움 | `exit`해도 컨테이너는 **계속 실행** (권장) |
| `Ctrl+P` 다음 `Ctrl+Q` | `-it`로 붙은 상태에서 떼어 내기(detach) | 컨테이너 계속 실행 |

컨테이너 ID는 다른 것과 구별되는 **앞 몇 글자**만 써도 됩니다(`docker exec -it efe9 /bin/bash`).

### 수명 주기

```bash
docker start   <ID|이름>     # 정지된 컨테이너 시작
docker restart <ID|이름>
docker stop    <ID|이름>     # 정상 종료 요청(SIGTERM → 유예 후 SIGKILL)
docker kill    <ID|이름>     # 즉시 강제 종료
docker rm      <ID|이름>     # 정지된 컨테이너 삭제  (-f 실행 중이어도 강제)
```

### 관찰·관리

```bash
docker top   <ID>            # 컨테이너 안 프로세스(UID, PID, PPID, CMD …)
docker inspect <ID>          # 설정 전체(JSON): 마운트, 환경 변수, 네트워크
docker logs  <ID>            # 표준 출력 로그   (-f 실시간, --tail 50)
docker stats <ID>            # CPU·메모리·네트워크·디스크 실시간
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' <ID>   # 컨테이너 IP
docker container prune       # 정지된 컨테이너 일괄 삭제
docker image prune           # 이름 없는(dangling) 이미지 삭제
docker volume create my-data # 이름 있는 볼륨 생성
```

:::danger MentorPi 컨테이너를 지우지 마세요
`mentorpi` 컨테이너 안에는 MentorPi의 모든 기능 코드와 **여러분이 컨테이너 레이어에 저장한 작업**이 들어 있습니다. 다음 명령은 로봇 위에서 절대 실행하지 않습니다.

- `docker rm -f $(docker ps -a -q)`, `docker ps -a -q | xargs docker rm` — **모든** 컨테이너 삭제
- `docker rmi -f $(docker images -qa)` — **모든** 이미지 삭제
- `docker system prune -a` — 사용 중이지 않은 이미지까지 삭제(컨테이너가 정지된 순간 실행하면 MentorPi 이미지도 대상)
- `docker container prune` — `mentorpi`가 **정지 상태**라면 함께 삭제됨

자기 작업은 공유 폴더(호스트 `~/docker` ↔ 컨테이너 `~/share`)에 두거나 `docker commit`으로 백업합니다.
:::

## 이미지 만들기

### 방법 1: `docker commit`(컨테이너 → 이미지)

컨테이너 안에서 패키지를 설치·수정한 상태를 그대로 이미지로 굳힙니다.

```bash
docker ps -a                                   # 대상 컨테이너 ID 확인
docker commit -m "add vim" -a "me" 9aeb4cc795e6 debian:1.0
docker images                                  # debian:1.0 추가 확인
```

간단하지만 **무엇을 바꿨는지 기록이 남지 않아** 재현성이 떨어집니다. MentorPi 컨테이너를 통째로 백업할 때는 유용합니다.

### 방법 2: Dockerfile(권장)

이미지를 만드는 절차를 텍스트로 적은 파일입니다. 한 명령(`RUN`, `COPY` …)이 대체로 **레이어 하나**가 됩니다.

```text
# Dockerfile — ROS 2 Humble 위에 내 노드를 올린 이미지
FROM ros:humble
RUN apt-get update && \
    apt-get install -y --no-install-recommends python3-pip vim && \
    rm -rf /var/lib/apt/lists/*            # 같은 RUN 안에서 캐시 삭제 → 레이어가 작아짐
RUN pip3 install --no-cache-dir numpy
WORKDIR /root/ws
COPY my_node.py .
ENV ROS_DOMAIN_ID=0
CMD ["bash", "-c", "source /opt/ros/humble/setup.bash && python3 my_node.py"]
```

```bash
docker build -t my-ros:1.0 .                 # 현재 폴더(.)의 Dockerfile 로 빌드
docker build -f dockerfile -t debian:1.1 .   # 파일 이름을 지정할 때 (원본 예)
docker run --rm -it --network=host my-ros:1.0
```

| 지시어 | 역할 |
|---|---|
| `FROM` | 바탕 이미지 |
| `RUN` | 빌드 중 명령 실행(레이어 생성) |
| `COPY`/`ADD` | 호스트 파일을 이미지로 복사 |
| `WORKDIR` | 작업 디렉터리 |
| `ENV` | 환경 변수 |
| `CMD` / `ENTRYPOINT` | 컨테이너 시작 시 실행할 기본 명령 |

Docker는 레이어를 **캐시**합니다. 앞 단계가 바뀌지 않으면 다시 빌드하지 않으므로, 자주 바뀌는 `COPY`는 뒤쪽에, 느린 `apt-get install`은 앞쪽에 둡니다.

## 하드웨어와 데이터 연결

### 장치

컨테이너는 기본적으로 호스트 장치를 보지 못합니다. 필요한 장치만 넘기거나(`--device`), `/dev` 전체를 마운트합니다(`-v /dev:/dev`, 보통 `--privileged`와 함께 — 편하지만 격리가 약해짐).

```bash
docker run -it --device=/dev/video0 debian:latest /bin/bash
ls /dev/          # 컨테이너 안에서 video0 확인
```

장치 이름이 부팅마다 바뀌지 않도록 호스트에 **udev 규칙**(`/etc/udev/rules.d/`)으로 고정 이름을 만들기도 합니다. MentorPi의 `/dev/rrc`(확장보드), `/dev/ldlidar`(라이다)가 이런 고정 이름입니다.

### GUI(X11)

RViz·turtlesim 같은 창을 컨테이너에서 띄우려면 호스트의 X 서버에 접근하게 해 줍니다.

```bash
sudo apt-get install x11-xserver-utils
xhost +                                   # X 서버 접근 허용(실습용. 끝나면 xhost - 권장)
docker run -it -e DISPLAY=$DISPLAY -e QT_X11_NO_MITSHM=1 \
  -v /tmp/.X11-unix:/tmp/.X11-unix debian:latest /bin/bash
apt-get update && apt-get install -y x11-apps
xeyes                                     # 마우스를 따라가는 눈이 뜨면 성공
```

### 파일 복사와 볼륨

```bash
docker cp d2d0e43b41eb:/root/test.txt ~/        # 컨테이너 → 호스트
docker cp test_1.txt d2d0e43b41eb:/root/         # 호스트 → 컨테이너 (컨테이너 실행 중)
docker run -it -v /home/pi/temp:/root/temp debian:latest /bin/bash   # 볼륨(바인드 마운트)
```

**데이터 볼륨**의 특징: 컨테이너끼리 공유·재사용 가능, 변경이 즉시 반영, 이미지 업데이트에 포함되지 않음, 컨테이너를 지워도 남음. 지도(`.pgm/.yaml`), 학습 데이터, rosbag처럼 **남겨야 하는 결과물**은 볼륨에 저장합니다.

## 컨테이너 안의 ROS 2

원본은 공식 `ros:humble` 이미지로 ROS 2 환경을 만드는 과정을 보여 줍니다(인터넷 필요, 시간이 오래 걸림). MentorPi 이미지는 이미 구성되어 있으므로 **학습용**입니다.

```bash
docker pull ros:humble
docker run -it --network=host -d -v=/dev:/dev -v /tmp/.X11-unix:/tmp/.X11-unix \
  --name humble -e DISPLAY=${DISPLAY} --restart=always ros:humble /bin/bash
xhost +
docker exec -it humble /bin/bash
# --- 컨테이너 안 (root) ---
useradd -m -s /bin/bash ubuntu && passwd ubuntu && usermod -aG sudo ubuntu
apt-get update && apt-get install -y sudo vim ros-humble-desktop-full    # 매우 오래 걸림
exit
docker exec -it -u ubuntu -w /home/ubuntu humble /bin/bash
source /opt/ros/humble/setup.bash
echo "source /opt/ros/humble/setup.bash" >> ~/.bashrc     # 새 터미널마다 자동 적용
ros2 run turtlesim turtlesim_node                         # 거북이 창이 뜨면 성공
```

:::info 원본과 다른 점
원본은 ROS 2 설치 확인에 `rosrun turtlesim turtlesim_node`를 적었지만, 이는 **ROS 1 명령**입니다. ROS 2에서는 `ros2 run turtlesim turtlesim_node`를 씁니다. 또 원본의 ROS 1(melodic) 예제는 `docker pull ros:melodic`으로 같은 절차를 따릅니다.
:::

옵션의 의미를 로봇 관점에서 정리하면:

| 옵션 | 왜 필요한가 |
|---|---|
| `--network=host` | ROS 2의 DDS는 **멀티캐스트로 서로를 발견**합니다. 컨테이너 전용 가상 네트워크에 있으면 PC·다른 로봇의 노드가 보이지 않을 수 있어 호스트 네트워크를 그대로 씁니다(R05). |
| `-v /dev:/dev` | 라이다·카메라·확장보드 직렬 장치를 컨테이너에서 사용 |
| `-v /tmp/.X11-unix` + `DISPLAY` | RViz 등 GUI |
| `--restart=always` | 로봇 전원을 켜면 컨테이너 자동 기동 |
| `-u ubuntu -w /home/ubuntu` | root가 아닌 일반 사용자로, 홈에서 시작 |

MentorPi 컨테이너도 같은 원리로 만들어져 있으며, 여러분은 B03에서 배운 대로 들어갑니다.

```bash
docker exec -it -u ubuntu -w /home/ubuntu mentorpi /bin/bash
```

## 이미지 배포: 저장소와 파일

### Docker Hub에 올리기

```bash
docker tag 30555f5a4f74 <사용자명>/debian:1.1    # 이름을 "사용자명/이미지:태그"로
docker login -u <사용자명>
docker push <사용자명>/debian:1.1
```

### tar 파일로 옮기기

| 방법 | 대상 | 명령 | 특징 |
|---|---|---|---|
| export / import | **컨테이너** | `docker export <ID> > debian.tar` → `cat debian.tar \| docker import - test/debian:v1` | 파일 시스템 한 장으로 평탄화(레이어·히스토리 없음), 더 작음, import 때 새 이름·태그 지정 |
| save / load | **이미지** | `docker save -o debian_1.1.tar debian:latest` → `docker load -i debian_1.1.tar` | 레이어·태그 그대로 보존 |

인터넷이 없는 실습실에서 여러 로봇에 같은 환경을 배포할 때 `save/load`가 유용합니다.

## 실습 (실물)

MentorPi 호스트 터미널에서 진행합니다. `debian` 이미지를 내려받는 단계는 인터넷이 필요하므로 **LAN 모드**로 연결해 둡니다(B02).

:::safety
- `mentorpi` 컨테이너와 이미지는 **삭제·정지·재생성하지 않습니다.** 실습은 `debian`·`hello-world`로 만든 **새 컨테이너**에서만 합니다.
- `docker rm`, `docker rmi`, `prune` 명령은 대상 ID가 **내가 만든 실습 컨테이너인지** `docker ps -a`로 확인한 뒤에만 실행합니다. 일괄 삭제 명령(`$(docker ps -a -q)`)은 쓰지 않습니다.
- SD 카드 여유 공간을 확인합니다(`df -h /`). `ros-humble-desktop-full` 설치는 수 GB가 필요하므로 로봇에서는 하지 않습니다.
- 실습이 끝나면 `xhost -`로 X 서버 접근을 다시 막습니다.
:::

:::task 따라 하기
1. `docker version`, `docker info | head -20`으로 설치 상태를 확인합니다.
2. `docker ps -a`에서 `mentorpi` 컨테이너의 이름·이미지·상태를 기록하고, `docker inspect mentorpi | grep -A3 '"Mounts"'`로 어떤 호스트 경로가 마운트되어 있는지 살펴봅니다(없으면 `docker inspect mentorpi | less`).
3. `docker stats --no-stream mentorpi`로 ROS 2 전체가 쓰는 CPU·메모리를 봅니다.
4. `docker run hello-world` → `docker images`
5. `docker pull debian` → `docker run -it --name lab1 -v ~/temp:/root/temp debian /bin/bash` → 컨테이너 안에서 `touch /root/temp/from_container.txt`, `touch /root/only_in_container.txt` → `exit`
6. 호스트에서 `ls ~/temp` → 볼륨 파일만 보이는 것 확인. `docker start lab1` 후 `docker exec -it lab1 ls /root`로 컨테이너 레이어 파일도 남아 있음을 확인
7. `docker cp lab1:/root/only_in_container.txt ~/` 로 꺼내기
8. `docker commit lab1 lab1-image:1.0` → `docker images` → `docker rm -f lab1` → `docker run --rm lab1-image:1.0 ls /root`로 커밋된 파일 확인
9. 정리: `docker rmi lab1-image:1.0` (자기 이미지만)
:::

:::check 체크포인트
- [ ] 컨테이너를 지우면 무엇이 사라지고 무엇이 남는지(컨테이너 레이어 vs 볼륨) 설명할 수 있다.
- [ ] `docker attach`와 `docker exec`의 종료 동작 차이를 안다.
- [ ] ROS 2 컨테이너에 `--network=host`를 주는 이유를 DDS 발견으로 설명할 수 있다.
- [ ] `export/import`와 `save/load`의 차이를 안다.
:::

## 자주 나는 오류와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| `permission denied while trying to connect to the Docker daemon socket` | 사용자가 `docker` 그룹이 아님 | `sudo gpasswd -a $USER docker` 후 재로그인(또는 재부팅) |
| `Unable to find image … locally` 후 멈춤·실패 | 인터넷 없음(AP 모드), 레지스트리 접속 불가 | LAN 모드 전환, 프록시·미러 확인 |
| `Conflict. The container name "/humble" is already in use` | 같은 이름의 컨테이너가 이미 있음 | `docker ps -a`로 확인, 다른 이름 사용 또는 기존 것 재사용(`docker start`) |
| `exit` 했더니 컨테이너가 멈춤 | `docker run -it`/`attach`로 PID 1 셸에 있었음 | 진입은 `docker exec`, 떼어 낼 때는 `Ctrl+P Ctrl+Q` |
| 컨테이너에서 만든 파일이 사라짐 | 컨테이너를 삭제(`rm`, `--rm`) | 볼륨·공유 폴더 사용, 필요 시 `commit` |
| 컨테이너 안에서 카메라·시리얼 장치가 없음 | `--device`/`-v /dev:/dev` 미지정 | 실행 옵션에 장치 추가(기존 컨테이너는 재생성 필요) |
| `cannot open display` / `Authorization required` | `DISPLAY` 미전달, `xhost +` 안 함, X11 소켓 미마운트 | 세 가지 옵션 확인 |
| PC의 ROS 2 노드가 컨테이너 토픽을 못 봄 | 브리지 네트워크, `ROS_DOMAIN_ID` 불일치 | `--network=host`, 같은 도메인 ID(R05) |
| `rosrun: command not found` | ROS 1 명령을 ROS 2에서 사용 | `ros2 run …` |
| 디스크가 가득 참 | 오래된 이미지·정지 컨테이너·빌드 캐시 | `docker system df`로 확인 후 **자기 것만** 정리 |
| 이미지가 예상보다 큼 | 다른 `RUN`에서 캐시 삭제(레이어에 이미 남음) | 설치와 정리를 같은 `RUN`에서, `--no-install-recommends` |
