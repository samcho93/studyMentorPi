## 학습 목표

- Nav2의 구성 요소(BT Navigator, Planner·Controller·Behavior·Smoother 서버, 코스트맵, 수명주기 관리자)와 MentorPi에서 속도 명령이 모터까지 가는 경로를 설명할 수 있습니다.
- 파티클 필터의 **예측(predict) → 갱신(update) → 재표본(resample)** 세 단계를 식과 코드로 구현합니다.
- AMCL의 움직임 모델(`alpha1~5`), 가능도장 센서 모델(`z_hit`, `sigma_hit`), KLD 적응 표본 수(`pf_err`, `pf_z`)를 MentorPi 파라미터 값으로 해석합니다.
- 코스트맵의 층(static·obstacle·voxel·inflation)과 비용 값(0, 253, 254, 255)의 의미를 말하고, MentorPi 설정의 특징(작은 `robot_radius`·`inflation_radius`)을 평가합니다.
- 실물에서 저장한 지도로 내비게이션을 띄우고 **2D Pose Estimate**로 초기 위치를 준 뒤 목표를 보냅니다.

## 내비게이션이 풀어야 할 문제

교재 표현대로 내비게이션은 "**내가 어디 있는지** 알고, **어디로 갈지** 정하고, 가는 동안 **부딪히지 않게** 속도를 내는" 일입니다. Nav2(Navigation 2)는 이것을 역할별 서버로 나눈 ROS 2 표준 스택입니다.

| 질문 | 담당 | MentorPi 구성 |
|---|---|---|
| 지도는? | `map_server` | `slam/maps/map_01.yaml` (M09에서 저장) |
| 나는 지도 어디에? | `amcl` | 파티클 필터, `map → odom` TF 발행 |
| 어떤 길로? | `planner_server` (전역) | `nav2_navfn_planner/NavfnPlanner` |
| 지금 얼마의 속도로? | `controller_server` (지역) | `dwb_core::DWBLocalPlanner` (또는 TEB) |
| 막히면? | `behavior_server` | spin, backup, drive_on_heading, wait, assisted_teleop |
| 전체 순서는? | `bt_navigator` | 행동 트리(Behavior Tree) XML |

## Nav2 구조

@fig[m11-nav2] MentorPi에서 Nav2가 목표를 받아 모터 명령을 내기까지: BT Navigator가 서버들을 액션으로 호출하고, 제어 명령은 velocity_smoother와 odom_publisher를 거쳐 모터로 갑니다.

### BT Navigator와 서버들

**BT Navigator**가 "주 서버"이고 나머지는 부품입니다. 행동 트리(behavior tree)는 "경로를 1 Hz로 다시 계산하면서 따라가고, 실패하면 코스트맵을 지우고 → 제자리 회전 → 후진을 시도하라" 같은 절차를 트리로 기술한 XML입니다. `nav2_params.yaml`의 `bt_navigator.plugin_lib_names`에 나오는 `nav2_compute_path_to_pose_action_bt_node`, `nav2_follow_path_action_bt_node`, `nav2_spin_action_bt_node`, `nav2_recovery_node_bt_node` … 가 트리의 잎(leaf) 노드들입니다.

| 서버 | 역할 (교재) | 입력 → 출력 |
|---|---|---|
| Planner Server | 지도 위 경로 계산 | 목표 + 전역 코스트맵 → `nav_msgs/Path` |
| Controller Server | ROS 1의 지역 계획기. 경로를 따라가는 속도 계산 | 경로 + 지역 코스트맵 + 오도메트리 → `cmd_vel` |
| Behavior Server | 교재의 "Recovery Server". 막혔을 때 스스로 빠져나옴 | spin, backup 등 |
| Smoother Server | 전역 경로 다듬기 | `nav2_smoother::SimpleSmoother` |
| Waypoint Follower | 여러 목표 순회 (M13) | |
| Velocity Smoother | 속도·가속 제한 | `cmd_vel_nav` → `cmd_vel` |

### 수명주기와 컨테이너

Nav2 노드는 **수명주기 노드**(lifecycle node)라서 unconfigured → inactive → active 상태를 거쳐야 일합니다. `lifecycle_manager_localization`(map_server, amcl)과 `lifecycle_manager_navigation`(controller_server, smoother_server, planner_server, behavior_server, bt_navigator, waypoint_follower, velocity_smoother)이 `autostart: true`로 이들을 순서대로 켭니다. MentorPi는 모든 노드를 `nav2_container`(`component_container_isolated`) 한 프로세스에 **컴포저블 노드**로 올려 메모리와 복사 비용을 줄입니다.

### launch 구조와 속도 명령 경로

`ros2 launch navigation navigation.launch.py map:=map_01`(원본 `navigation/launch/navigation.launch.py`):

| 단계 | 파일 | 내용 |
|---|---|---|
| base_launch | `slam/launch/include/robot.launch.py` | 컨트롤러·EKF·라이다·깊이 카메라 (M09와 같음) |
| 10 s 후 | `navigation/launch/include/bringup.launch.py` | `nav2_container` + `localization.launch.py` + `navigation_base.launch.py` |
| localization | `include/localization.launch.py` | `nav2_map_server::MapServer`, `nav2_amcl::AmclNode` |
| navigation | `include/navigation_base.launch.py` | 컨트롤러 파라미터: `use_teb` 인자에 따라 `config/nav2_controller_dwb.yaml`(기본) 또는 `nav2_controller_teb.yaml` |

소스를 따라가면 속도 명령은 이렇게 흐릅니다.

```text
controller_server  --cmd_vel_nav-->  velocity_smoother  --cmd_vel-->  odom_publisher (app_cmd_vel_callback)
                                     max [0.26, 0, 1.0]                |linear| ≤ 0.2 m/s, |angular| ≤ 0.5 rad/s 로 자름
                                                                        → 메카넘/애커만 역기구학 → 모터
```

DWB의 `max_vel_x`는 0.4 m/s, velocity_smoother의 `max_velocity`는 0.26 m/s이지만, 마지막에 `odom_publisher_node.py`의 `app_cmd_vel_callback`이 `/cmd_vel`을 **0.2 m/s, 0.5 rad/s로 한 번 더 자릅니다**(R03, M04). 실제 내비게이션 속도 상한은 이 값입니다. 안전장치이니 그대로 둡니다.

## 위치추정: AMCL

### 왜 필요한가

오도메트리 `odom → base_footprint`는 부드럽고 빠르지만 **드리프트**가 쌓입니다. AMCL(Adaptive Monte Carlo Localization)은 라이다 스캔을 저장된 지도와 비교해 **지도 기준 위치**를 추정하고, 그 차이를 `map → odom` 변환으로 발행합니다. 결과 TF 체인은 `map → odom → base_footprint → lidar_frame`입니다. 교재 말대로 `map → odom`을 내는 것은 AMCL 대신 SLAM, UWB, QR 코드 위치추정 등 무엇이든 될 수 있습니다(M13의 RTAB-Map이 그 예).

### 베이즈 필터와 파티클

위치추정은 **믿음**(belief) $bel(xₜ)$ — "지금 로봇이 xₜ에 있을 확률 분포"를 갱신하는 문제입니다.

| 단계 | 식 | 뜻 |
|---|---|---|
| 예측 | $bel⁻(xₜ) = ∫ p(xₜ \| uₜ, xₜ₋₁) · bel(xₜ₋₁) dxₜ₋₁$ | 움직임 모델로 믿음을 옮기고 퍼뜨림 |
| 갱신 | $bel(xₜ) = η · p(zₜ \| xₜ) · bel⁻(xₜ)$ | 관측이 잘 설명되는 곳의 믿음을 키움 |

분포를 식으로 들고 다니는 대신 **표본(파티클) N개**로 들고 다니는 것이 파티클 필터입니다. 파티클 하나 = "로봇이 여기 있을지도 모른다"는 가설 $(x, y, θ)$와 가중치 $w$.

@fig[m11-pf] 파티클 필터 한 주기: 예측(움직임 + 잡음) → 갱신(스캔 가능도로 가중치) → 재표본(무거운 파티클 복제, 가벼운 파티클 제거).

1. **예측**: 오도메트리가 "0.25 m 전진, 5° 회전"이라고 하면 모든 파티클을 그만큼 옮기되, **각자 다른 잡음**을 더합니다. 잡음 크기가 `alpha1~5`입니다.
2. **갱신**: 각 파티클 자리에서 스캔을 지도에 겹쳐 보고 가능도 $p(z | x)$를 가중치로 곱합니다. 벽과 잘 맞는 파티클이 무거워집니다.
3. **재표본**: 가중치에 비례해 파티클을 다시 뽑습니다. 무거운 파티클은 여러 번 복제되고 가벼운 것은 사라집니다. **저분산(체계적) 재표본**은 난수 하나로 N개를 등간격으로 뽑아 표본 편향을 줄입니다.
4. **추정**: 가중 평균과 공분산이 로봇 위치와 불확실성입니다(RViz의 초록 화살표 구름과 타원).

### 실습: 1D 파티클 필터

문 세 개(1.5, 4.0, 7.0 m)가 있는 10 m 복도에서, 로봇이 **자기 위치를 전혀 모른 채**(파티클을 복도 전체에 균일하게 뿌림) 0.5 m씩 이동하며 "문이 보인다/안 보인다"만으로 위치를 찾습니다. 순수 numpy 코드라 결과가 매번 같습니다.

@btn[~/tools/playground.html] Playground 열기

```python run
import numpy as np

rng = np.random.default_rng(0)
DOORS = np.array([1.5, 4.0, 7.0])       # 복도(0~10 m)의 문 위치 = 지도
N, STEP, SIG_MOVE = 500, 0.5, 0.1        # 파티클 수, 한 번 이동량, 이동 잡음

def near_door(x):                        # 문 앞(±0.3 m)이면 True
    return np.min(np.abs(x[:, None] - DOORS[None, :]), axis=1) < 0.3

def likelihood(z, x):                    # 센서 모델 p(z | x): 적중률 0.9
    w = np.where(near_door(x) == z, 0.9, 0.1)
    return np.where((x < 0.0) | (x > 10.0), 1e-3, w)   # 복도 밖 = 지도상 벽

def low_variance_resample(p, w):         # 체계적(저분산) 재표본
    u = (rng.random() + np.arange(N)) / N
    idx = np.searchsorted(np.cumsum(w), u)
    return p[np.minimum(idx, N - 1)]

true_x = 0.5
p = rng.uniform(0.0, 10.0, N)            # 전역 위치추정: 복도 전체에 균일 분포
w = np.full(N, 1.0 / N)
print("step true   z      mean   std   N_eff")
for k in range(14):
    # 1) 예측: 이동 명령 u = +0.5 m에 잡음을 더해 모든 파티클을 옮김
    true_x += STEP
    p = p + STEP + rng.normal(0.0, SIG_MOVE, N)
    # 2) 갱신: 관측 z(문 보임?)의 가능도로 가중치 곱하고 정규화
    z = bool(near_door(np.array([true_x]))[0])
    w = w * likelihood(z, p)
    w = w / w.sum()
    n_eff = 1.0 / np.sum(w ** 2)
    mean = np.sum(w * p)
    std = np.sqrt(np.sum(w * (p - mean) ** 2))
    print("%4d %5.2f  %-5s %6.2f %5.2f %6.1f" % (k + 1, true_x, z, mean, std, n_eff))
    # 3) 재표본: 유효 파티클 수가 절반 밑으로 떨어지면
    if n_eff < N / 2:
        p = low_variance_resample(p, w)
        w = np.full(N, 1.0 / N)
```

읽는 법:

- 2단계에서 첫 문을 봤지만 **어느 문인지 모릅니다.** 파티클이 세 문 앞에 모여 평균(5.15)은 의미 없고 표준편차가 큽니다(다봉 분포).
- 7단계에서 두 번째 문을 보면 "문 → 2.5 m 뒤 문" 패턴과 어긋나는 가설이 약해져 표준편차가 2.0 → 1.3 m로 줄고, 13단계 세 번째 문에서 0.47 → 0.23 m로 수렴합니다. 문 간격이 2.5 m와 3.0 m로 **다르기 때문에** 가능한 일입니다. 모든 간격이 같다면 끝까지 구별하지 못합니다(대칭 환경의 함정).
- `N_eff`(유효 파티클 수 $1/Σw²$)는 가중치가 한쪽에 쏠릴수록 작아집니다. 문을 본 단계(2, 7, 13)에서 크게 떨어지고, 그때 재표본이 일어납니다.

:::tip 직접 바꿔 보기
`N`을 50으로 줄이면 올바른 가설 근처에 파티클이 하나도 안 남아 **엉뚱한 곳으로 수렴**하는 경우가 생깁니다(파티클 고갈). `SIG_MOVE`를 0으로 두면 재표본 뒤 복제본이 모두 같은 자리에 겹쳐 다양성이 사라집니다. AMCL의 `alpha` 잡음과 `min_particles`가 필요한 이유입니다.
:::

### AMCL 파라미터 (MentorPi 값)

`navigation/config/nav2_params.yaml`의 `amcl:` 절입니다.

| 분류 | 파라미터 | 값 | 뜻 |
|---|---|---|---|
| 파티클 수 | `min_particles` / `max_particles` | 500 / 3000 | KLD 적응 표본 수의 하한·상한 |
| | `pf_err` / `pf_z` | 0.05 / 0.99 | KLD 오차 한계와 분위수(아래 설명) |
| | `resample_interval` | 1 | 필터 갱신마다 재표본 |
| 갱신 조건 | `update_min_d` / `update_min_a` | 0.25 m / 0.2 rad | 이만큼 움직여야 필터를 갱신 (정지 중 과신 방지) |
| 움직임 모델 | `robot_model_type` | `nav2_amcl::DifferentialMotionModel` | 차동 구동 잡음 모델 |
| | `alpha1` ~ `alpha5` | 모두 0.2 | 1: 회전이 만드는 회전 잡음, 2: 이동이 만드는 회전 잡음, 3: 이동이 만드는 이동 잡음, 4: 회전이 만드는 이동 잡음, 5: 횡이동 잡음(Omni 모델 전용) |
| 센서 모델 | `laser_model_type` | `likelihood_field` | 가능도장 모델 |
| | `max_beams` | 60 | 한 스캔에서 쓰는 빔 수 (360개 중 균등 추출) |
| | `laser_min_range` / `laser_max_range` | 0.2 / 10.0 m | 이 범위 밖 빔 무시 |
| | `z_hit` / `z_rand` | 0.5 / 0.5 | 정상 측정 / 무작위 잡음 성분 비중 |
| | `z_short` / `z_max` | 0.05 / 0.05 | 빔 모델용 (가능도장에서는 영향 적음) |
| | `sigma_hit` | 0.2 m | 측정점-가장 가까운 벽 거리의 가우시안 표준편차 |
| | `laser_likelihood_max_dist` | 2.0 m | 가능도장 거리 계산 상한 |
| 복구 | `recovery_alpha_slow` / `recovery_alpha_fast` | 0.0 / 0.0 | 0이면 무작위 파티클 주입(납치 로봇 복구) 끔 |
| 프레임 | `global_frame_id` / `odom_frame_id` / `base_frame_id` | map / odom / base_footprint | |
| | `scan_topic` | `scan_raw` | |
| | `tf_broadcast` / `transform_tolerance` | true / 1.0 s | `map → odom` 발행, TF 허용 지연 |
| 초기 자세 | `set_initial_pose` / `initial_pose` | True / (0, 0, 0) | 시작 시 (0, 0, 0)으로 가정 |

**가능도장 모델**(likelihood field): 지도에서 각 셀과 가장 가까운 벽까지의 거리 $d$를 미리 계산해 두고, 스캔 끝점이 떨어진 셀의 $d$로 가능도를 계산합니다.

$p(zₖ | x) = z_hit · N(d; 0, sigma_hit²) + z_rand / z_max_range$

MentorPi는 `z_rand` = 0.5로 **무작위 성분을 크게** 잡았습니다. 지도에 없는 사람·의자가 많은 실내에서 이상한 빔 하나가 가중치를 0으로 만들지 않게 하는 보수적 설정입니다.

**KLD 적응 표본 수**: 파티클들이 차지하는 격자 칸(bin) 수 k가 많으면(= 위치를 잘 모르면) 파티클을 늘리고, 몰려 있으면 줄입니다. nav2_amcl은 다음 식을 쓰고, `pf_z` 값을 분위수 z로 그대로 넣습니다.

$n = (k − 1)/(2·pf_err) · (1 − 2/(9(k−1)) + √(2/(9(k−1))) · pf_z)³$

| 차지한 bin 수 k | 계산된 n | 실제 파티클 수 (500~3000으로 자름) |
|---|---|---|
| 10 | 131 | 500 |
| 50 | 588 | 588 |
| 100 | 1129 | 1129 |
| 200 | 2188 | 2188 |
| 300 | 3232 | 3000 |

초기 위치를 잘 찍어 주면 k가 작아 500개로 가볍게 돌고, 위치를 잃으면 최대 3000개까지 늘어납니다. 교재의 "적은 표본으로 실시간성을 높인다"가 이 뜻입니다.

:::warning 메카넘 로봇인데 Differential 모델?
MentorPi 설정은 섀시와 관계없이 `DifferentialMotionModel`입니다. 메카넘으로 **옆으로** 이동하면 이 모델은 횡이동을 예측하지 못해 파티클이 뒤처지고, 스캔이 맞춰 줄 때까지 위치가 튈 수 있습니다. 메카넘에서 횡이동을 많이 쓸 계획이면 `nav2_amcl::OmniMotionModel`(이때 `alpha5` 사용)로 바꿔 비교해 볼 만합니다. 기본 DWB 설정은 `max_vel_y: 0.0`이라 내비게이션 중에는 횡이동을 쓰지 않습니다.
:::

## 코스트맵

지도(0/100/−1)는 그대로 경로 계획에 쓰지 못합니다. 로봇은 점이 아니라 크기가 있기 때문입니다. Nav2는 지도를 **코스트맵**(costmap, 셀당 1바이트 0~255)으로 바꿔 씁니다.

| 비용 값 | 이름 | 뜻 |
|---|---|---|
| 0 | FREE_SPACE | 자유 |
| 1~252 | 팽창 비용 | 장애물에 가까울수록 큼 |
| 253 | INSCRIBED_INFLATED_OBSTACLE | 로봇 **중심**이 여기 오면 몸체가 장애물에 닿음 |
| 254 | LETHAL_OBSTACLE | 장애물 셀 자체 |
| 255 | NO_INFORMATION | 모름 |

코스트맵은 **층(layer) 플러그인**을 쌓아 만듭니다. 교재가 설명하는 `Costmap2D`/`Layer` 클래스 구조에서 `initialize`·`matchSize`는 한 번, `updateBounds`·`updateCosts`는 `update_frequency`마다 호출됩니다. 장애물 층은 스캔 빔을 따라 **Bresenham 선**으로 셀을 비우고(clearing) 끝점을 채웁니다(marking) — M09의 역센서 모델과 같은 일입니다.

| 항목 | 전역 코스트맵 (`global_costmap`) | 지역 코스트맵 (`local_costmap`) |
|---|---|---|
| 쓰는 곳 | Planner Server | Controller Server |
| 좌표계 | `map` | `odom`, `rolling_window: true` (로봇 따라 이동) |
| 크기·해상도 | 지도 전체, 0.05 m | 3 × 3 m, **0.03 m** |
| 갱신 / 발행 | 1.0 / 1.0 Hz | 5.0 / 2.0 Hz |
| 층 | `static_layer`, `obstacle_layer`, `inflation_layer` | `voxel_layer`, `inflation_layer` |
| `robot_radius` | 0.05 m | 0.05 m |
| 팽창 | `inflation_radius` 0.05, `cost_scaling_factor` 5.0 | `inflation_radius` 0.05, `cost_scaling_factor` 2.0 |
| 관측 | `/scan_raw`, `obstacle_max_range` 2.5, `raytrace_max_range` 3.0 | 같음 + `z_voxels` 16 × `z_resolution` 0.03 |
| 모름 영역 | `track_unknown_space: true` | |

:::danger `robot_radius` 0.05 m는 실제 로봇보다 작다
URDF(M08)의 바퀴 위치만 봐도 로봇 중심에서 바퀴까지 약 0.1 m이고, 차체 외곽은 그보다 큽니다. `robot_radius: 0.05`, `inflation_radius: 0.05`이면 코스트맵은 로봇을 **지름 10 cm 공**으로 보고, 팽창도 사실상 없습니다. 좁은 틈으로 경로를 내서 차체 모서리가 벽이나 의자 다리에 걸릴 수 있습니다. 원본 값의 의도(좁은 공간 통과)를 이해하되, 실습 공간이 좁지 않다면 M12에서 `robot_radius` 0.12~0.15 m, `inflation_radius` 0.25~0.3 m로 바꿔 비교합니다. 팽창 비용식과 튜닝은 M12에서 다룹니다.
:::

@btn[~/sim/index.html] 2D 시뮬레이터 열기

1. **room** 월드에서 **SLAM** 모드로 지도를 먼저 만듭니다(M09).

## 실습 (실물)

:::safety
- 내비게이션은 **로봇이 스스로 움직입니다.** 목표를 보내기 전에 경로 주변에 사람·애완동물·깨지기 쉬운 물건이 없는지 확인하고, 한 사람은 항상 로봇 곁에 있습니다.
- 첫 시험 목표는 **1 m 이내, 탁 트인 곳**으로 잡습니다.
- 속도는 `app_cmd_vel_callback`의 0.2 m/s, 0.5 rad/s로 제한됩니다. 이 제한을 풀지 않습니다.
- 멈출 때: RViz Navigation 2 패널의 **Cancel**, 또는 launch 터미널 Ctrl+C. 계속 움직이면 `ros2 topic pub --once /controller/cmd_vel geometry_msgs/msg/Twist "{}"`, 최후에는 전원 스위치.
- 계단·경사로가 있는 곳에서는 하지 않습니다. 2D 라이다는 아래로 꺼진 곳을 보지 못합니다.
:::

1. M09에서 저장한 지도(`~/ros2_ws/src/slam/maps/map_01.yaml`)가 있는지 확인하고 내비게이션을 띄웁니다.

```bash
# 로봇
~/.stop_ros.sh
ls ~/ros2_ws/src/slam/maps
ros2 launch navigation navigation.launch.py map:=map_01

# 가상머신 (M09에서 준비한 워크스페이스)
ros2 launch navigation rviz_navigation.launch.py
```

2. 약 10 s 뒤 Nav2가 활성화됐는지 확인합니다.

```bash
ros2 lifecycle get /amcl                 # active [3]
ros2 lifecycle get /bt_navigator         # active [3]
ros2 param get /amcl max_particles       # 3000
```

3. RViz 도구 모음의 **2D Pose Estimate**를 누르고, 지도에서 로봇의 실제 위치를 클릭한 채 **로봇이 바라보는 방향으로 끌었다 놓습니다.** 파티클 구름(`/particle_cloud`)이 그 주변에 모이고, 스캔(빨간 점)이 지도의 벽과 겹치는지 봅니다. 어긋나면 다시 찍습니다. CLI로도 줄 수 있습니다.

```bash
ros2 topic pub --once /initialpose geometry_msgs/msg/PoseWithCovarianceStamped \
  "{header: {frame_id: map}, pose: {pose: {position: {x: 0.0, y: 0.0}, orientation: {z: 0.0, w: 1.0}}}}"
```

4. 로봇을 제자리에서 조금 회전시키거나 0.3 m쯤 움직이면(`update_min_d` 0.25 m, `update_min_a` 0.2 rad) 필터가 갱신되며 구름이 좁아집니다.
5. **Nav2 Goal**(교재의 "2D Nav Goal")로 목표를 클릭·드래그합니다. 초록 선(직선 참고선)과 진한 파란 선(계획된 경로)이 나타나고 로봇이 출발합니다. CLI로 목표를 줄 수도 있습니다.

```bash
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: 1.0, y: 0.0}, orientation: {w: 1.0}}}}" --feedback
```

6. 경로 위에 상자를 놓아 로봇이 돌아가는지(지역 코스트맵의 voxel 층) 확인합니다. 끝나면 Ctrl+C 후 호스트 터미널에서 `sudo systemctl restart start_node.service`.

:::check 체크포인트
- [ ] 예측·갱신·재표본이 각각 무엇을 바꾸는지(파티클 위치 / 가중치 / 파티클 집합) 말할 수 있다.
- [ ] 2D Pose Estimate를 잘못 찍었을 때와 잘 찍었을 때 파티클 구름과 스캔 정합을 비교했다.
- [ ] Nav2의 속도 명령이 모터까지 가는 경로와, 실제 상한이 0.2 m/s인 이유를 설명할 수 있다.
:::

## 자주 나는 오류와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| RViz에 지도가 안 뜸 | 지도 이름 오타, 10 s 지연 전, `map_server` inactive | `map:=` 값과 `slam/maps/*.yaml` 이름 일치 확인, `ros2 lifecycle get /map_server` |
| 목표를 줘도 "Robot is out of bounds"/경로 없음 | 초기 위치 미설정, 로봇 위치가 벽 속 | 2D Pose Estimate로 실제 위치·방향 지정 |
| 스캔이 지도 벽과 어긋난 채 수렴 | 초기 방향 틀림, 대칭 환경 | 방향까지 정확히 다시 지정, 특징 있는 곳에서 조금 움직이기 |
| 로봇이 제자리에서 계속 돌기만 함 (spin 복구 반복) | 경로 추종 실패 → 행동 트리 복구 | 코스트맵에 가짜 장애물이 있는지 확인, `clear costmap` 후 재시도 |
| 좁은 틈에서 차체가 긁힘 | `robot_radius`·`inflation_radius` 0.05 m | M12에서 값 상향 후 비교 |
| "Timed out waiting for transform from base_footprint to map" | AMCL이 아직 TF를 안 냄, 초기 자세 없음 | 초기 자세 지정, `/amcl` 로그 확인 |
| 목표 근처에서 멈추지 않고 맴돎 | 목표 허용오차보다 제어가 거칢 | `xy_goal_tolerance`·`yaw_goal_tolerance`(0.25) 확인 (M12) |

1. 1D 파티클 필터에서 문 위치를 `[1.5, 4.0, 6.5]`(간격이 모두 2.5 m)로 바꿔 실행하고, 수렴이 어떻게 달라지는지 설명합니다.
2. KLD 식으로 k = 20, 150일 때 파티클 수를 계산하고, `min_particles`를 100으로 바꾸면 어떤 장단점이 있을지 씁니다.

3. 1D 코드에 **납치 로봇**(kidnapped robot) 상황을 넣습니다: 10단계에서 `true_x`를 2.0으로 순간 이동시키고, 무작위 파티클을 일부(예: 5 %) 주입하는 코드를 추가해 복구되는지 봅니다. AMCL의 `recovery_alpha_slow/fast`가 이 기능이며 MentorPi에서는 0(꺼짐)인 이유를 토론합니다.

:::
