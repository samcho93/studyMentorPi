## 학습 목표

- Telegram 메시지가 Bot API 서버 → Gateway → 에이전트 → 답장으로 흐르는 **최소 동작 루프**를 설명합니다.
- BotFather로 봇을 만들고 토큰을 발급·보관·폐기(revoke)하는 방법을 익힙니다.
- `openclaw config set`, `openclaw gateway`, `openclaw pairing approve`로 Telegram 채널을 연결합니다.
- 페어링·허용 목록(allowFrom)·DM/그룹 정책을 **접근 제어**로 이해하고, 로봇 봇을 열어 두면 왜 위험한지 설명합니다.
- 롱 폴링(long polling)과 웹훅(webhook)의 차이, 채널·사용자별 세션 분리(dmScope)를 모형으로 확인합니다.

## 최소 동작 루프

지금까지는 터미널의 `openclaw agent` 명령으로만 에이전트와 대화했습니다. 실제 비서나 로봇은 **휴대폰 메신저**로 부를 수 있어야 쓸모가 커집니다. OpenClaw에서 메신저 연결을 **채널(channel)**이라고 부르며, 이 장에서는 그중 Telegram을 연결합니다.

원본 교재는 이 장을 다음 장(이메일 에이전트)의 첫 부분으로 소개합니다. 완성될 전체 루프는 이렇습니다.

```text
Telegram 메시지 → Gateway가 이메일 에이전트로 라우팅 → email-fetch(메일 가져오기)
  → mail-agent(구조화 분석) → 결과를 채팅으로 다시 전송
```

| 구성 요소 | 역할 |
|---|---|
| **Gateway** | Telegram 이벤트를 받고, 누구의 어떤 대화인지 세션을 정해 에이전트로 보냄 |
| **Agent** | 어떤 워크플로를 탈지 판단하고 필요한 스킬을 고름 |
| **Skills** | 메일 가져오기·분석·전송 같은 개별 기능 |
| **Workflow** | 가져오기 → 분석 → 전송을 정해진 순서로 연결 |

이 장은 그중 가장 먼저 필요한 부분, **Telegram을 Gateway에 연결하는 것**만 다룹니다. 이메일은 C07, 로봇 제어는 C08에서 이 채널 위에 올립니다.

@fig[c06-flow] 메시지의 경로. Gateway는 Bot API 서버에 새 메시지가 있는지 먼저 묻고(롱 폴링), 받은 메시지를 접근 제어 → 세션 키 → 에이전트 순으로 넘긴 뒤 sendMessage로 답합니다.

## Telegram 봇의 동작 원리

### Bot API와 토큰

Telegram 봇은 사람 계정이 아니라 **Bot API**라는 HTTP 인터페이스로 움직이는 특수 계정입니다. 모든 요청은 `https://api.telegram.org/bot<토큰>/메서드이름` 형태로 보내며, 여기서 **토큰(token)**이 봇의 신분증이자 비밀번호입니다. 토큰을 아는 사람은 누구든 그 봇으로 메시지를 읽고 보낼 수 있습니다. 로봇에 연결된 봇이라면 **로봇을 조종할 수 있는 열쇠**가 되는 셈입니다.

### 롱 폴링과 웹훅

봇 프로그램이 새 메시지를 받는 방법은 두 가지입니다.

| 방식 | 동작 | 장점 | 필요 조건 |
|---|---|---|---|
| **롱 폴링** (`getUpdates`) | 봇이 "새 메시지 있나요?"라고 묻고, 서버는 메시지가 올 때까지 잠시 붙잡고 있다가 답함 | 바깥으로 나가는 연결만 필요 → 집·학교 공유기 뒤에서도 동작 | 봇이 계속 실행 중이어야 함 |
| **웹훅** (`setWebhook`) | 메시지가 오면 Telegram 서버가 봇의 HTTPS 주소로 밀어 줌 | 지연이 짧고 요청 수가 적음 | 외부에서 접근 가능한 HTTPS 주소 |

MentorPi나 연구실 PC처럼 공인 주소가 없는 장치에는 롱 폴링이 자연스럽습니다. 롱 폴링에서 중요한 개념은 **offset**입니다. 매 업데이트에는 증가하는 `update_id`가 붙고, 다음 요청에 `offset = 마지막 update_id + 1`을 보내면 서버는 그 이전 업데이트를 "처리 완료"로 보고 다시 보내지 않습니다. 아래 모형은 Bot API의 `getUpdates` 응답 모양을 흉내 낸 것입니다.

```python run
# 롱 폴링 흉내: getUpdates(offset) — 확인한 업데이트는 다시 오지 않는다
server_queue = [
    {"update_id": 5001, "message": {"message_id": 1, "from": {"id": 111, "first_name": "Minji"},
                                    "chat": {"id": 111, "type": "private"}, "text": "/start"}},
    {"update_id": 5002, "message": {"message_id": 2, "from": {"id": 111, "first_name": "Minji"},
                                    "chat": {"id": 111, "type": "private"}, "text": "hello"}},
]
arrivals = {2: {"update_id": 5003, "message": {"message_id": 3, "from": {"id": 222, "first_name": "Guest"},
                                               "chat": {"id": 222, "type": "private"}, "text": "로봇 앞으로 가"}}}

def get_updates(offset, timeout=30):
    # offset 이전 업데이트는 '확인됨'으로 보고 서버가 버린다
    global server_queue
    server_queue = [u for u in server_queue if u["update_id"] >= offset]
    return {"ok": True, "result": list(server_queue)}

offset = 0
for poll in range(1, 4):
    if poll in arrivals:
        server_queue.append(arrivals[poll])
    res = get_updates(offset)["result"]
    ids = [u["update_id"] for u in res]
    for u in res:
        m = u["message"]
        print(f"  poll {poll}: from {m['from']['id']} ({m['chat']['type']}) → {m['text']!r}")
    if res:
        offset = res[-1]["update_id"] + 1       # 다음 요청에서 확인 처리
    print(f"poll {poll}: 받은 update_id={ids or '없음(타임아웃까지 대기)'} → 다음 offset={offset}")
```

```text
  poll 1: from 111 (private) → '/start'
  poll 1: from 111 (private) → 'hello'
poll 1: 받은 update_id=[5001, 5002] → 다음 offset=5003
  poll 2: from 222 (private) → '로봇 앞으로 가'
poll 2: 받은 update_id=[5003] → 다음 offset=5004
poll 3: 받은 update_id=없음(타임아웃까지 대기) → 다음 offset=5004
```

같은 토큰으로 **두 프로그램이 동시에 폴링**하면 서로 업데이트를 가져가 버려 메시지가 사라진 것처럼 보이고, Bot API는 충돌(409 Conflict) 오류를 돌려줍니다. 한 봇 토큰은 한 Gateway에서만 쓰는 것이 원칙입니다. 또 로그의 `111`, `222` 같은 `from.id`가 Telegram의 **숫자 사용자 ID**이며, 아래 허용 목록은 이 값을 기준으로 합니다.

## 접근 제어: 누구의 말을 들을 것인가

Telegram 봇은 **사용자 이름만 알면 전 세계 누구나** 말을 걸 수 있습니다. 봇의 사용자 이름은 검색되고, 추측도 쉽습니다(`..._bot`). 평범한 챗봇이라면 모르는 사람이 말을 걸어도 API 요금이 좀 나가는 정도지만, **파일 쓰기·스크립트 실행·로봇 이동 권한을 가진 에이전트**라면 이야기가 다릅니다. 모르는 사람의 "로봇 앞으로 가"가 그대로 실행되면 안 됩니다.

OpenClaw는 채널 설정에서 이를 막는 장치를 제공합니다(키 이름과 기본값은 버전에 따라 다를 수 있습니다).

| 설정 | 의미 | 값의 예 |
|---|---|---|
| `dmPolicy` | 1:1 대화(DM)를 받는 규칙 | `pairing`(승인된 사람만), `allowlist`, `open`, `disabled` |
| `allowFrom` | DM을 허용할 사용자 ID 목록 | `[123456789]`, 모두 허용은 `["*"]` |
| `groupPolicy` | 그룹 대화를 받는 규칙 | `allowlist`, `open`, `disabled` |

**페어링(pairing)**은 처음 보는 사용자에게 짧은 코드를 보내고, 서버 관리자가 터미널에서 그 코드를 승인해야 대화가 열리는 방식입니다. 승인 전 메시지는 에이전트에게 전달되지 않습니다. 비밀번호 대신 **서버에 접근할 수 있는 사람의 확인**을 신뢰의 근거로 삼는 셈입니다.

:::warning 원본 예시 설정의 open 정책
원본 교재 7장의 설정 예시에는 편의상 `"dmPolicy": "open"`, `"allowFrom": ["*"]`, `"groupPolicy": "open"`이 들어 있습니다. 시연에는 편하지만 **누구나 에이전트를 쓸 수 있는 상태**입니다. 이메일이나 로봇을 다루는 에이전트에서는 반드시 `pairing` 또는 `allowlist`로 바꾸고, 허용할 사람의 숫자 ID만 적으세요.
:::

아래 모형은 DM은 페어링, 그룹은 허용된 그룹 ID만 받는 게이트입니다(설명용으로 단순화한 것이며, 실제 설정 키 이름과 다릅니다).

```python run
# 접근 제어 게이트: dmPolicy=pairing, groupPolicy=allowlist + 세션 키
import random
rng = random.Random(7)                    # 결정적 페어링 코드
config = {"dmPolicy": "pairing", "groupPolicy": "allowlist",
          "allowFrom": [], "allowed_groups": [-100500]}
pending = {}                              # code -> user_id

def pairing_code():
    return "".join(rng.choice("ABCDEFGHJKLMNPQRSTUVWXYZ23456789") for _ in range(8))

def gate(msg):
    uid, chat = msg["from"]["id"], msg["chat"]
    if chat["type"] == "private":
        if uid in config["allowFrom"] or config["dmPolicy"] == "open":
            return "PASS", f"telegram:dm:{uid}"
        if config["dmPolicy"] == "pairing":
            code = next((c for c, u in pending.items() if u == uid), None) or pairing_code()
            pending[code] = uid
            return "PAIR", f"페어링 코드 {code} 발송 (에이전트에는 전달 안 함)"
        return "DROP", "DM 차단"
    if chat["id"] in config["allowed_groups"]:
        return "PASS", f"telegram:group:{chat['id']}"
    return "DROP", "허용되지 않은 그룹"

def approve(code):                        # openclaw pairing approve telegram <code>
    uid = pending.pop(code)
    config["allowFrom"].append(uid)
    return uid

def msg(uid, chat_id, ctype, text):
    return {"from": {"id": uid}, "chat": {"id": chat_id, "type": ctype}, "text": text}

inbox = [msg(111, 111, "private", "/start"), msg(222, 222, "private", "로봇 앞으로 가"),
         msg(333, -100999, "group", "@bot 사진 찍어"), msg(111, -100500, "group", "@bot 상태")]
for m in inbox:
    v, detail = gate(m)
    print(f"{m['from']['id']}/{m['chat']['type']:7s} → {v}: {detail}  ({m['text']})")

first_code = next(iter(pending))
print("\n승인:", first_code, "→ user", approve(first_code))
for m in [msg(111, 111, "private", "hello"), msg(222, 222, "private", "로봇 앞으로 가")]:
    v, detail = gate(m)
    print(f"{m['from']['id']}/{m['chat']['type']:7s} → {v}: {detail}  ({m['text']})")
print("allowFrom =", config["allowFrom"], "| 대기 중 코드 =", list(pending))
```

```text
111/private → PAIR: 페어링 코드 WK3DEGZD 발송 (에이전트에는 전달 안 함)  (/start)
222/private → PAIR: 페어링 코드 PCF54ERF 발송 (에이전트에는 전달 안 함)  (로봇 앞으로 가)
333/group   → DROP: 허용되지 않은 그룹  (@bot 사진 찍어)
111/group   → PASS: telegram:group:-100500  (@bot 상태)

승인: WK3DEGZD → user 111
111/private → PASS: telegram:dm:111  (hello)
222/private → PAIR: 페어링 코드 PCF54ERF 발송 (에이전트에는 전달 안 함)  (로봇 앞으로 가)
allowFrom = [111] | 대기 중 코드 = ['PCF54ERF']
```

사용자 222의 "로봇 앞으로 가"는 승인 전이므로 끝까지 에이전트에 닿지 않습니다. 관리자는 **자기가 요청한 코드만** 승인해야 합니다. 누군가 "이 코드 좀 승인해 주세요"라고 코드를 보내온다면, 그것은 모르는 사람에게 로봇 열쇠를 건네는 일입니다.

## 세션 라우팅: 대화를 섞지 않기

허용된 메시지는 **세션(session)**에 담겨 에이전트로 갑니다. 세션은 대화 맥락(이전 발화, 도구 결과)의 묶음이므로, 어떤 메시지를 같은 세션으로 볼지가 곧 **누가 누구의 대화를 볼 수 있는지**를 정합니다. 원본 설정의 `"session": { "dmScope": "per-channel-peer" }`는 **채널과 상대방마다 별도 세션**을 만든다는 뜻입니다. 아래 모형으로 범위별 차이를 비교해 봅시다(세션 키 문자열 모양은 설명용입니다).

```python run
# 세션 범위(dmScope)에 따라 대화 맥락이 섞이는지 비교
events = [("telegram", 111, "내 사물함 번호는 302번이야, 기억해"),
          ("telegram", 222, "안녕, 방금 누가 뭐라고 했어?"),
          ("feishu",   111, "아까 말한 사물함 번호 뭐였지?")]

def session_key(scope, channel, peer):
    if scope == "main":
        return "agent:main:main"                       # 모든 DM이 한 세션
    if scope == "per-peer":
        return f"agent:main:dm:{peer}"                 # 사람별 (채널 무관)
    if scope == "per-channel-peer":
        return f"agent:main:{channel}:dm:{peer}"       # 채널+사람별
    raise ValueError(scope)

for scope in ["main", "per-peer", "per-channel-peer"]:
    sessions = {}
    print(f"[dmScope={scope}]")
    for ch, peer, text in events:
        key = session_key(scope, ch, peer)
        history = sessions.setdefault(key, [])
        leak = [h for h in history if h[0] != peer]    # 다른 사람의 발화가 맥락에 있나?
        mark = "  ← 다른 사용자 맥락 노출!" if leak else ""
        print(f"  {ch}/{peer} → {key}  (맥락 {len(history)}개){mark}")
        history.append((peer, text))
    print(f"  세션 수: {len(sessions)}")
```

```text
[dmScope=main]
  telegram/111 → agent:main:main  (맥락 0개)
  telegram/222 → agent:main:main  (맥락 1개)  ← 다른 사용자 맥락 노출!
  feishu/111 → agent:main:main  (맥락 2개)  ← 다른 사용자 맥락 노출!
  세션 수: 1
[dmScope=per-peer]
  telegram/111 → agent:main:dm:111  (맥락 0개)
  telegram/222 → agent:main:dm:222  (맥락 0개)
  feishu/111 → agent:main:dm:111  (맥락 1개)
  세션 수: 2
[dmScope=per-channel-peer]
  telegram/111 → agent:main:telegram:dm:111  (맥락 0개)
  telegram/222 → agent:main:telegram:dm:222  (맥락 0개)
  feishu/111 → agent:main:feishu:dm:111  (맥락 0개)
  세션 수: 3
```

`main`은 혼자 쓰는 개인 비서라면 편하지만(어느 채널에서 말해도 이어짐), 여러 사람이 쓰는 봇에서는 **다른 사람의 말이 내 대화 맥락에 섞입니다**. `per-peer`는 사람별로 나누지만, 실제로는 채널마다 사용자 ID 체계가 달라 같은 숫자가 같은 사람이라는 보장이 없습니다(모형의 111은 설명을 위한 가정). `per-channel-peer`는 가장 보수적인 선택이며, 로봇처럼 여러 사람이 접근할 수 있는 에이전트에 권장됩니다.

## 실습 (실물)

:::safety 실습 전 확인
- **봇 토큰은 비밀번호입니다.** 화면 공유·스크린샷·깃 저장소·질문 게시판에 올리지 마세요. 문서와 명령 예시에서는 항상 `<TELEGRAM_BOT_TOKEN>` 같은 자리표시자를 씁니다.
- 이 장에서 연결하는 에이전트(`main`)가 `exec` 같은 강한 도구를 가지고 있다면, 페어링을 끝내기 전까지 봇 사용자 이름을 다른 사람에게 알리지 마세요.
- 로봇 제어 도구를 붙이는 것은 C08에서 합니다. 이 장에서는 **대화 연결만** 확인하고, 에이전트가 로봇을 움직일 수 있는 상태에서 채널을 열지 않습니다.
- 페어링 코드는 **자기가 직접 받은 것만** 승인합니다.
:::

### 2) BotFather로 봇 만들기

1. 검색창에서 **BotFather**를 찾습니다. 이름 옆에 **파란 인증 표시**가 있는 공식 계정인지 반드시 확인합니다. 비슷한 이름의 가짜 계정이 토큰을 가로채는 경우가 있습니다.
2. 대화창에 `/newbot`을 보냅니다.
3. 표시 이름(name)을 정합니다. 예: `MentorPi Lab Assistant`
4. 사용자 이름(username)을 정합니다. **반드시 `_bot` 또는 `bot`으로 끝나야** 하며 전 세계에서 유일해야 합니다. 예: `mentorpi_lab_assistant_bot`
5. BotFather가 **토큰**을 보여 줍니다. 모양은 `123456789:AA...`처럼 `숫자:영문자열`입니다. 이 값을 안전한 곳(비밀번호 관리자 등)에 옮겨 둡니다.

:::tip 토큰이 샜다면: /revoke
토큰이 노출되었다고 의심되면 BotFather에서 `/mybots` → 해당 봇 → API Token → **Revoke current token**(또는 `/revoke` 명령)으로 즉시 폐기하고 새 토큰을 받습니다. 옛 토큰은 그 순간부터 쓸 수 없으므로, 새 토큰으로 OpenClaw 설정을 바꾸고 Gateway를 재시작합니다. 정기적으로 토큰을 교체(rotation)하는 습관도 좋습니다.
:::

### 3) OpenClaw에 Telegram 채널 연결

```bash
# 1. Telegram 채널(플러그인) 활성화
openclaw config set channels.telegram.enabled true

# 2. 봇 토큰 등록 — <TELEGRAM_BOT_TOKEN> 자리에 실제 토큰을 넣는다
openclaw config set channels.telegram.botToken "<TELEGRAM_BOT_TOKEN>"

# 3. Gateway 기동 (이 터미널은 계속 열어 둔다)
openclaw gateway
```

`config set`은 `~/.openclaw/openclaw.json`의 해당 키를 고쳐 줍니다. 명령에 토큰을 직접 치면 셸 기록(`~/.bash_history`)에 남으므로, 등록 뒤 `history -d`로 지우거나 명령 앞에 공백을 넣어 기록되지 않게 하는(`HISTCONTROL=ignorespace`일 때) 방법을 씁니다. 설정 파일 자체도 `chmod 600 ~/.openclaw/openclaw.json`으로 본인만 읽게 해 둡니다.

### 4) START와 페어링

@fig[c06-pairing] 페어링 순서. Gateway가 먼저 떠 있어야 START에 대한 페어링 코드가 옵니다. 코드 승인은 서버 터미널에서만 할 수 있습니다.

1. BotFather의 안내 메시지에 있는 봇 링크(`t.me/<봇사용자이름>`)를 눌러 봇 대화창을 열고 **START**를 누릅니다. **`openclaw gateway`가 먼저 실행 중이어야** 코드가 옵니다.
2. 봇이 **페어링 코드**를 보냅니다.
3. **새 터미널**을 열어 승인합니다. `<code>` 자리에 받은 코드를 넣고, 꺾쇠괄호는 입력하지 않습니다.

```bash
openclaw pairing approve telegram <code>
```

4. 봇에게 `hello`를 보냅니다. AI 비서처럼 답하면 연결 완료입니다.

:::check 합격 기준
- 승인한 계정에서 `hello`에 답이 온다.
- **다른 Telegram 계정**(친구·두 번째 계정)으로 말을 걸면 답 대신 페어링 코드만 오고, 승인하지 않는 한 대화가 열리지 않는다.
- Gateway를 끄면 봇이 답하지 않고, 다시 켜면 그동안 쌓인 메시지를 처리한다(롱 폴링의 offset 동작).
:::

## 자주 나는 오류와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| START를 눌러도 페어링 코드가 안 옴 | Gateway가 꺼진 상태에서 START | `openclaw gateway` 실행 후 다시 메시지 보내기 |
| Gateway 로그에 401 Unauthorized | 토큰 오타, 따옴표·공백 포함, 폐기된 토큰 | BotFather에서 토큰 재확인, `config set`으로 다시 등록 |
| 409 Conflict / 메시지가 가끔 사라짐 | 같은 토큰으로 다른 프로그램이 폴링 중, 또는 웹훅이 설정됨 | 다른 봇 프로세스 종료, 웹훅 해제(`deleteWebhook`) |
| `pairing approve`가 코드를 모른다고 함 | 코드 오타(꺾쇠 포함), 만료, 다른 채널 이름 | 꺾쇠 없이 입력, 새 코드 받기, 채널은 `telegram` |
| 그룹에서 봇이 반응 없음 | `groupPolicy`가 막음, 봇의 개인정보 모드(privacy mode)로 일반 메시지 미수신 | 그룹 허용 설정 확인, 봇을 멘션하거나 BotFather `/setprivacy` 검토 |
| 봇이 답은 하는데 이상한 맥락을 기억 | `dmScope`가 `main`이라 대화가 섞임 | `per-channel-peer`로 변경 후 재시작 |
| `username`이 거부됨 | `bot`으로 끝나지 않음, 이미 사용 중 | `_bot`으로 끝나는 다른 이름 |

## 과제

1. **(기본)** 롱 폴링 모형에서 offset 갱신 줄을 주석 처리하고 실행해 보세요. 어떤 일이 일어나는지, 실제 봇이라면 사용자가 무엇을 겪게 될지 설명하세요.
2. **(기본)** 접근 제어 모형에 `dmPolicy = "allowlist"`를 추가하세요. 이 모드에서는 코드를 보내지 않고 목록에 없는 사용자를 조용히 무시합니다. pairing과 비교해 장단점을 쓰세요.
3. **(심화)** 로봇 제어 봇을 연구실 5명이 함께 쓴다고 가정하고, `dmPolicy`·`allowFrom`·`groupPolicy`·`dmScope` 값을 정한 뒤 각각의 이유와 토큰 교체 주기를 포함한 **운영 규칙 한 쪽**을 작성하세요.
4. **(심화)** 실물에서 두 번째 Telegram 계정으로 봇에 말을 걸어, 승인 전후의 Gateway 로그를 비교하고 페어링이 실제로 메시지를 막는지 확인하세요.
:::
