## 학습 목표

- 모델(Model)과 에이전트(Agent)의 역할을 "두뇌"와 "작업 관리자"로 구분해 설명합니다.
- 도구 호출 루프(모델의 도구 호출 요청 → 런타임 실행 → 결과 추가 → 반복)를 파이썬 모의 모델로 직접 돌리고 `max_iterations`의 의미를 말합니다.
- 도구가 호출되지 않을 때 모델보다 먼저 확인할 설정(`tools.allow`/`tools.deny`, 재시작)을 나열합니다.
- 단기·장기 메모리가 대화 맥락을 어떻게 유지하는지 보이고, 컨텍스트 창이 넘칠 때 생기는 문제를 재현합니다.
- 워크플로와 스킬(`SKILL.md` + 코드)의 차이, 그리고 Tool과 Skill의 관계를 예로 설명합니다.

## 한눈에 보는 여섯 개념

C01에서 본 구성 요소 가운데 에이전트가 **일을 처리하는 방식**에 관여하는 여섯 개념을 이 장에서 하나씩 뜯어 봅니다.

| 개념 | 한 줄 정의 | 비유 | OpenClaw에서 보이는 곳 |
|---|---|---|---|
| **Model** | 이해하고 생성하는 두뇌 | 두뇌 | `models.providers`, `agents.defaults.model` |
| **Agent** | 목표를 향해 다음 행동을 정하는 작업 관리자 | 담당 직원 | `agents.list`, 워크스페이스 파일 |
| **Tool** | 외부 세계와 상호작용하는 단일 기능 | 손 | `tools.allow` / `tools.deny` |
| **Memory** | 맥락과 선호를 유지 | 수첩 | 세션 기록, `MEMORY.md` 같은 파일 |
| **Workflow** | 여러 단계를 순서·분기·오류 처리와 함께 배열 | 업무 절차서 | 스킬 안의 단계, 워크플로 파일(C07) |
| **Skill** | 자주 쓰는 능력을 묶은 재사용 모듈 | 업무 매뉴얼 + 전용 도구 세트 | `SKILL.md` + 코드(C05) |

## 모델(Model): 두뇌

모델은 두 가지 일을 합니다. **이해**(요청의 의도와 맥락 파악)와 **생성**(답, 단계, 형식 있는 출력 만들기)입니다. "제품 소개 글을 써 줘"라는 요청을 받으면 제품의 위치, 대상 독자, 어조를 먼저 파악하고 글을 만듭니다. 입력(메시지와 맥락)을 받아 출력(텍스트)을 돌려주는 함수라고 생각하면 됩니다.

모델마다 강점이 다릅니다. 복잡한 추론에 강한 모델, 빠르고 저렴해서 잦은 질의응답에 맞는 모델, 코드나 JSON 같은 구조화 출력에 강한 모델이 있습니다. 하지만 이 단계에서 "최고의 모델"을 고를 필요는 없습니다. **모델을 바꾸면 답의 품질이 달라지지만, AI가 어떤 역할을 하고 어떻게 쓰이는지는 에이전트와 설정이 정합니다.**

OpenClaw는 여러 공급자의 모델을 가능한 한 통일된 방식으로 연결하므로, 모델을 바꿔도 프로젝트 전체를 다시 짤 필요가 없습니다. 설정 파일의 모델 항목에는 보통 다음 정보가 들어갑니다(필드 이름은 버전에 따라 조금씩 다릅니다).

| 필드 | 의미 | 예 |
|---|---|---|
| `provider` | 모델 공급자 | `deepseek`, `openai`, `ollama` |
| `baseUrl` | API 엔드포인트(필요할 때) | `https://api.deepseek.com` |
| `apiKey` | 비공개 API 키 | `sk-...` (절대 공개 저장소에 올리지 않음) |
| model id | 모델 이름 | `deepseek-chat` |

에이전트는 모델을 `공급자/모델ID` 형태로 참조합니다. 예를 들어 원본 교재의 설정은 기본 모델을 `deepseek/deepseek-chat`, 특정 에이전트의 모델을 `deepseek/deepseek-reasoner`로 지정합니다.

## 에이전트(Agent): 작업 관리자

모델이 두뇌라면 에이전트는 **다음에 무엇을 할지 결정하고, 도구가 필요한지 판단하고, 작업을 끝까지 밀고 가는 비서**입니다. 답 한 번을 돌려주고 끝나는 것이 아니라 목표를 기준으로 행동을 이어 갑니다.

"오늘 뉴욕 날씨 보고 우산 챙겨야 하는지 알려 줘"라는 요청을 에이전트는 이렇게 처리합니다.

1. 요청에 **날씨 정보**와 **추천** 두 부분이 있음을 파악합니다.
2. 날씨는 추측하면 안 되고 외부에서 가져와야 한다고 판단합니다.
3. 날씨 도구(또는 스킬)를 호출합니다.
4. 강수확률과 기온 같은 결과를 받습니다.
5. 결과를 "우산을 챙기세요" 같은 분명한 추천으로 바꿔 답합니다.

에이전트가 무엇을 할지는 **프롬프트, 워크스페이스 규칙 파일, 도구·스킬 권한**에 달려 있습니다(C04).

### 실행 스타일

구현은 버전마다 다르지만 에이전트의 행동은 대략 세 가지 스타일로 볼 수 있습니다. 외울 필요는 없고, "에이전트는 질문에 답하는 것이 아니라 일을 끝내는 것"이 핵심입니다.

| 스타일 | 동작 | 장점 | 단점 | 로봇 예 |
|---|---|---|---|---|
| **생각하며 행동**(think-and-act, ReAct) | 추론 → 도구 호출 → 결과 관찰 → 다시 추론을 반복 | 결과를 보고 유연하게 방향 수정 | 호출 횟수·비용 예측이 어려움 | "장애물 거리 보고 괜찮으면 전진" |
| **계획 후 실행**(plan-then-execute) | 먼저 3~7단계 계획을 세우고 차례로 실행 | 진행 상황이 투명, 사람이 계획을 검토 가능 | 중간에 상황이 바뀌면 계획이 낡음 | "순찰: 거실→주방→현관, 각 지점 사진" |
| **대화형**(chat-oriented) | 여러 턴의 대화, 되묻기에 적합 | 모호한 요청을 질문으로 좁힘 | 스스로 행동을 덜 함 | "어디로 가라는 건가요?" 되묻기 |

C04의 `test` 에이전트는 시스템 프롬프트로 "복잡한 목표는 먼저 3~7단계로 분해하고 단계마다 쓸 도구를 적으라"고 지시해, 계획 후 실행 스타일을 유도합니다.

## 도구(Tool): 손

모델은 아무리 똑똑해도 혼자서는 **텍스트만** 만들 수 있습니다. 실제로 행동하려면 도구가 필요합니다. 흔한 도구 능력은 다음과 같습니다.

- 실시간 정보 조회(날씨, 시간), 웹 검색·페이지 가져오기
- 파일·규칙·문서 읽기, 허가된 경우 파일 쓰기
- 업무 시스템 API 호출
- 계산(모델의 암산보다 정확한 수치·규칙 처리)

"지금 뉴욕은 몇 시야?"를 모델 혼자 답하면 틀리기 쉽습니다. 모델이 학습된 시점과 지금이 다르고, 모델에는 시계가 없기 때문입니다. 에이전트는 시간 도구를 불러 실제 값을 받고, 그 값을 문장으로 다듬어야 합니다. **도구는 추측을 줄이고, 외부 정보 접근과 행동을 가능하게 합니다.**

### 도구 호출 루프

도구가 실제로 어떻게 불리는지 알아 두면 디버깅이 쉬워집니다. 대부분의 LLM API(OpenAI, Anthropic, DeepSeek 등)와 에이전트 런타임은 같은 원리를 씁니다.

@fig[c02-loop] 도구 호출 루프. 모델은 도구를 직접 실행하지 않고 "이 도구를 이 인자로 불러 달라"는 구조화된 요청(JSON)만 돌려줍니다.

1. 런타임이 대화 기록과 **사용 가능한 도구 목록(이름, 설명, 인자 형식)**을 모델에 보냅니다.
2. 모델은 둘 중 하나를 돌려줍니다. **최종 답(텍스트)** 또는 **도구 호출 요청** `{"name": "get_weather", "arguments": "{\"city\": \"뉴욕\"}"}`.
3. 도구 호출이면 런타임이 **권한을 검사**하고 실제 함수를 실행합니다.
4. 실행 결과를 `tool` 역할의 메시지로 대화에 **덧붙이고** 다시 모델을 부릅니다.
5. 최종 답이 나오거나 **최대 반복 횟수(max iterations)**에 닿을 때까지 2~4를 반복합니다.

최대 반복 횟수는 안전장치입니다. 도구가 계속 실패하는데 모델이 같은 호출을 되풀이하면 비용이 끝없이 늘고, 로봇이라면 같은 동작을 반복할 수 있습니다. 아래 모의 코드에서 두 경우를 모두 봅시다. `MockModel`은 실제 LLM 대신 규칙으로 동작하지만, 주고받는 메시지 형식은 실제와 같은 구조입니다.

@btn[~/tools/playground.html] Playground 열기

```python run
# 도구 호출 루프: 모델이 도구 호출(JSON)을 내면 런타임이 실행하고 결과를 붙여 다시 묻습니다.
import json

def get_weather(city):
    table = {"뉴욕": {"rain_prob": 70, "temp_c": 18}, "서울": {"rain_prob": 10, "temp_c": 24}}
    return table.get(city, {"error": "unknown city"})

def calc(expr):
    a, op, b = expr.split()
    return {"value": float(a) * float(b) if op == "*" else float(a) + float(b)}

TOOLS = {"get_weather": get_weather, "calc": calc}

class MockModel:
    """규칙 기반 가짜 LLM. 실제 모델도 '도구 호출' 또는 '최종 답' 둘 중 하나를 돌려줍니다."""
    def complete(self, messages):
        last = messages[-1]
        if last["role"] == "user":
            city = "뉴욕" if "뉴욕" in last["content"] else "서울"
            return {"tool_call": {"name": "get_weather", "arguments": json.dumps({"city": city})}}
        if last["role"] == "tool":
            data = json.loads(last["content"])
            if "error" in data:      # 고집 센 모델: 실패한 호출을 그대로 다시 시도
                return {"tool_call": messages[-2]["tool_call"]}
            if "rain_prob" in data:
                tip = "우산을 챙기세요" if data["rain_prob"] >= 50 else "우산은 필요 없습니다"
                return {"final": "강수확률 %d%%, %d°C - %s." % (data["rain_prob"], data["temp_c"], tip)}

def run_agent(model, user_text, allow, max_iterations=4):
    messages = [{"role": "user", "content": user_text}]
    for i in range(1, max_iterations + 1):
        out = model.complete(messages)
        if "final" in out:
            print("  [%d] 최종 답: %s" % (i, out["final"]))
            return out["final"]
        call = out["tool_call"]
        args = json.loads(call["arguments"])
        print("  [%d] 도구 호출 요청: %s(%s)" % (i, call["name"], args))
        if call["name"] not in allow:
            result = {"error": "tool '%s' not allowed" % call["name"]}
        else:
            result = TOOLS[call["name"]](**args)
        print("      결과: %s" % result)
        messages.append({"role": "assistant", "tool_call": call})
        messages.append({"role": "tool", "content": json.dumps(result, ensure_ascii=False)})
    print("  최대 반복(%d) 도달 - 중단" % max_iterations)

print("질문 1 (도구 허용)")
run_agent(MockModel(), "오늘 뉴욕 날씨 보고 우산 필요한지 알려줘", allow={"get_weather", "calc"})
print("질문 2 (get_weather 금지)")
run_agent(MockModel(), "서울 우산 필요해?", allow={"calc"}, max_iterations=3)
```

  [2] 최종 답: 강수확률 70%, 18°C - 우산을 챙기세요.
질문 2 (get_weather 금지)

  [2] 도구 호출 요청: get_weather({'city': '서울'})

질문 2에서 `get_weather`는 허용 목록에 없어 매번 오류가 돌아가고, 고집 센 모델은 같은 호출을 되풀이하다 3회 제한에 걸려 멈춥니다. 실제 모델은 보통 오류 메시지를 읽고 "날씨 도구를 쓸 수 없습니다"라고 답하지만, 그렇지 않은 경우도 있으므로 반복 제한은 반드시 있어야 합니다.

### 도구가 호출되지 않을 때

모든 도구가 모든 에이전트에 자동으로 열리는 것은 아닙니다. 도구 접근은 설정과 권한으로 제어됩니다(도구 프로필 활성화, `tools.allow`와 `tools.deny`). 에이전트가 도구를 안 쓰면 **모델을 탓하기 전에 설정부터** 확인합니다.

1. 도구가 활성화되어 있는가? (도구 프로필, 플러그인)
2. 이 에이전트의 권한이 허용하는가? `deny`에 있으면 `allow`에 있어도 막힐 수 있습니다.
3. 설정을 바꾼 뒤 **Gateway를 재시작**해 최신 설정이 적용되었는가?
4. (그다음에) 도구 설명이 모호해서 모델이 언제 써야 할지 모르는가?

:::warning deny는 allow보다 강하다고 생각하세요
같은 도구가 `allow`와 `deny`에 모두 있으면 대부분의 권한 시스템은 **거부를 우선**합니다. 설정이 헷갈리면 결과를 추측하지 말고 C03의 점검 실습처럼 겹침부터 찾아 없애세요.
:::

## 메모리(Memory): 맥락

메모리는 대화를 매번 처음부터 시작하지 않게 해 줍니다. "Python을 배우고 싶어" 다음에 "그거 초보자한테 괜찮아?"라고 물으면, "그거"가 Python이라는 것을 알아야 제대로 답할 수 있습니다.

| 종류 | 담는 것 | 수명 | 보관 위치(일반적) |
|---|---|---|---|
| **단기 메모리** | 최근 대화 턴, 방금 말한 핵심 정보 | 현재 세션 | 세션 기록(모델에 매번 함께 전송) |
| **장기 메모리** | 선호, 자주 쓰는 용어, 요약 노트 | 세션을 넘어 유지 | 파일·장기 기록(예: `MEMORY.md`, C07) |

중요한 사실 하나: 모델 자체는 기억이 없습니다. 런타임이 **이전 메시지를 매번 다시 보내 주기 때문에** 기억하는 것처럼 보입니다. 모델이 한 번에 받을 수 있는 양(컨텍스트 창, context window)에는 한계가 있으므로 오래된 메시지는 잘라 내거나 요약해야 하고, 그러다 필요한 맥락이 사라질 수 있습니다. 아래 예제는 창 크기에 따라 "그거"를 이해하는지가 갈리는 모습을 보여 줍니다.

```python run
# 단기 기억(최근 N턴) + 장기 기억(메모 파일 역할) 흉내
long_term = {}              # 실제로는 MEMORY.md 같은 파일
TOPICS = ["Python", "ROS 2", "라이다"]

def find_topic(history):
    # '그거/그것'이 무엇인지: 최근 대화에서 가장 마지막에 나온 주제를 찾습니다.
    for msg in reversed(history):
        for t in TOPICS:
            if t in msg:
                return t
    return None

def reply(history, text, window):
    if text.startswith("기억해:"):
        k, v = text[4:].split("=")
        long_term[k.strip()] = v.strip()
        return "메모함 (%s)" % k.strip()
    if "그거" in text or "그것" in text:
        topic = find_topic(history[-window:])   # 최근 window개 메시지만 전달
        if topic is None:
            return "무엇을 말씀하시는지 모르겠습니다."
        level = long_term.get("수준", "미상")
        return "%s 말씀이죠? (사용자 수준: %s) 초보자도 시작할 수 있습니다." % (topic, level)
    return "알겠습니다."

def chat(turns, window):
    history = []
    for t in turns:
        r = reply(history, t, window)
        history += [t, r]
        print("  나> %s  /  비서> %s" % (t, r))

turns = ["Python을 배우고 싶어", "기억해: 수준 = 완전 초보",
         "주말에 시간이 있어", "그거 초보자한테 괜찮아?"]
print("창 크기 8 (충분)")
chat(turns, window=8)
print("창 크기 4 (Python 언급이 창 밖으로 밀려남)")
chat(turns, window=4)
print("장기 기억:", long_term)
```

```text
창 크기 8 (충분)
  나> Python을 배우고 싶어  /  비서> 알겠습니다.
  나> 기억해: 수준 = 완전 초보  /  비서> 메모함 (수준)
  나> 주말에 시간이 있어  /  비서> 알겠습니다.
  나> 그거 초보자한테 괜찮아?  /  비서> Python 말씀이죠? (사용자 수준: 완전 초보) 초보자도 시작할 수 있습니다.
창 크기 4 (Python 언급이 창 밖으로 밀려남)
  나> Python을 배우고 싶어  /  비서> 알겠습니다.
  나> 기억해: 수준 = 완전 초보  /  비서> 메모함 (수준)
  나> 주말에 시간이 있어  /  비서> 알겠습니다.
  나> 그거 초보자한테 괜찮아?  /  비서> 무엇을 말씀하시는지 모르겠습니다.
장기 기억: {'수준': '완전 초보'}
```

창이 4일 때 "Python" 언급은 창 밖으로 밀려나 "그거"를 해석하지 못합니다. 반면 "기억해:"로 장기 메모리에 적은 `수준 = 완전 초보`는 창과 관계없이 남습니다. 오래 유지해야 할 정보는 단기 기록에 기대지 말고 장기 메모리로 옮기는 이유가 여기에 있습니다.

## 워크플로(Workflow): 실행 계획

한 번에 끝나지 않는 작업은 단계로 나눠 순서대로 실행해야 합니다. "판매 보고서를 준비해 줘"는 데이터 읽기 → 정리 → 통계 분석 → 보고서 생성의 네 단계입니다. 에이전트가 작업 책임자라면 워크플로는 **실행 계획서**로, 다음을 정합니다.

1. 무엇을 먼저 하는가
2. 다음에 무엇을 하는가
3. 오류가 나면 어떻게 하는가
4. 반복이나 분기가 필요한가

워크플로의 장점은 단계가 명확하고, 빠뜨리거나 순서가 뒤바뀔 위험이 적고, 한번 안정되면 비슷한 작업에 재사용할 수 있다는 것입니다. 로봇에서는 특히 **"오류가 나면 어떻게 하는가"**가 중요합니다. 센서 하나가 응답하지 않을 때 전체를 멈출지, 그 항목만 "확인 불가"로 둘지 미리 정해 둬야 합니다.

## 스킬(Skill): 재사용 모듈

스킬은 자주 쓰는 기능을 미리 묶어 둔 **재사용 가능한 능력 모듈**입니다. 문서 처리(읽기·요약·핵심 추출), 코드 처리, 데이터 분석, 검색 요약, 환경이 지원하면 멀티모달 처리 등이 흔한 예입니다.

@fig[c02-tool-skill] Tool은 하나의 동작이고, Skill은 "언제·어떻게 부를지"를 적은 `SKILL.md`와 "부른 뒤 무엇을 할지"를 담은 코드로 여러 도구를 엮은 모듈입니다.

| 구분 | Tool | Skill |
|---|---|---|
| 크기 | 단일 기능 (`web_fetch`, `read`, `exec`) | 여러 도구 + 절차 + 출력 형식 |
| 구성 | 런타임이 제공하는 함수 | `SKILL.md`(메타데이터) + 코드(예: `index.js`의 `run(input)`) |
| 모델에게 알려 주는 것 | 이름, 설명, 인자 형식 | 이름, 트리거 상황, 입출력 설명, 단계, 제약 |
| 사용자 정의 | 보통 플러그인 수준 | 사용자 업무 능력을 만들 때 **우선 선택** |

정리하면 **`SKILL.md`는 모델에게 언제, 어떻게 스킬을 부를지 알려 주고, 코드는 부른 뒤 실제로 무엇이 일어나는지 정합니다.** C05에서 일일 브리핑·날씨 스킬을 처음부터 작성합니다. 아래 예제는 로봇 상태 보고 스킬을 흉내 냅니다. 트리거 문구로 스킬이 선택되고, 스킬 내부 워크플로가 도구 세 개를 순서대로 부르며, 실패한 단계는 규칙에 따라 추측 대신 "확인 불가"로 채웁니다.

```python run
# Tool(단일 동작) vs Skill(메타데이터 + 여러 도구를 엮은 절차 + 고정 출력 형식)
def tool_read_battery():   return {"voltage": 7.6}
def tool_read_scan():      return {"min_range_m": 0.42}
def tool_read_odom():      raise TimeoutError("odom 토픽 응답 없음")

SKILL_MD = {                       # SKILL.md가 모델에게 알려 주는 내용의 요약
    "name": "robot-status-briefing",
    "triggers": ["상태 보고", "점검해"],
    "output": "배터리: {bat} / 최근접 장애물: {obs} / 위치: {pos}",
    "rules": ["값을 못 얻으면 '확인 불가'로 쓰고 추측하지 않는다"],
}

def run_skill(_input):
    # Workflow: 정해진 순서로 단계 실행, 단계별 오류 처리
    steps = [("bat", tool_read_battery, lambda r: "%.1f V" % r["voltage"]),
             ("obs", tool_read_scan,    lambda r: "%.2f m" % r["min_range_m"]),
             ("pos", tool_read_odom,    lambda r: "(%.1f, %.1f)" % (r["x"], r["y"]))]
    filled = {}
    for i, (key, tool, fmt) in enumerate(steps, 1):
        try:
            filled[key] = fmt(tool())
            print("  단계 %d %-18s 성공" % (i, tool.__name__))
        except Exception as e:
            filled[key] = "확인 불가"        # rules: 날조 금지
            print("  단계 %d %-18s 실패 (%s)" % (i, tool.__name__, e))
    return SKILL_MD["output"].format(**filled)

def agent(text):
    for trig in SKILL_MD["triggers"]:
        if trig in text:
            print("스킬 선택: %s (트리거 '%s')" % (SKILL_MD["name"], trig))
            return run_skill(text)
    return "스킬 없이 일반 답변: " + text

print(agent("로봇 상태 보고 부탁해"))
print(agent("오늘 기분 어때?"))
```

```text
스킬 선택: robot-status-briefing (트리거 '상태 보고')
  단계 1 tool_read_battery  성공
  단계 2 tool_read_scan     성공
  단계 3 tool_read_odom     실패 (odom 토픽 응답 없음)
배터리: 7.6 V / 최근접 장애물: 0.42 m / 위치: 확인 불가
스킬 없이 일반 답변: 오늘 기분 어때?
```

위치를 못 읽었다고 "(0.0, 0.0)"처럼 그럴듯한 값을 지어내지 않는 것, 이것이 C05에서 강조하는 **날조 금지** 규칙입니다. 고정 출력 형식 덕분에 사람도, 다른 프로그램도 결과를 안정적으로 읽을 수 있습니다.

## 개념들이 맞물리는 방식

여섯 개념은 요청 하나 안에서 다음 파이프라인으로 이어집니다.

```text
요청 도착
  └─ Agent가 작업을 이해하고 다음 행동 결정 ── Model이 추론/생성
        ├─ 외부 정보나 행동이 필요한가? ── 예 → Tool 또는 Skill 호출 → 결과를 다시 Model로
        ├─ 맥락이 필요한가?              ── 예 → Memory 읽기/쓰기
        ├─ 여러 단계의 복잡한 작업인가?   ── 예 → Workflow로 단계별 실행
        └─ 모두 아니오 → 최종 결과 반환
```

OpenClaw는 모델 하나가 아니라, **두뇌(모델)·손(도구)·수첩(메모리)·절차서(워크플로)·매뉴얼(스킬)을 엮어 대화에서 행동으로 넘어가게 하는 시스템**입니다.

## 자주 나는 오류와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| 에이전트가 도구 없이 날씨·시간을 지어냄 | 도구가 비활성·미허용, 또는 규칙에 "조회 필수"가 없음 | 도구 권한 확인, 워크스페이스 규칙에 "실시간 정보는 도구로" 명시 |
| 도구를 허용했는데 호출이 안 됨 | `deny`에도 있음, 설정 변경 후 미재시작 | allow/deny 겹침 제거, `openclaw gateway restart` |
| 같은 도구를 계속 반복 호출 | 도구 오류가 해결되지 않음 | 최대 반복 제한 확인, 오류 메시지를 명확히, 원인(권한·인자) 수정 |
| 앞에서 한 말을 잊음 | 다른 세션이거나 컨텍스트 창 초과 | 같은 `session-id` 사용, 중요한 정보는 장기 메모리로 |
| 스킬이 선택되지 않음 | 트리거 문구가 요청과 다름, 스킬 미등록 | `SKILL.md` 트리거 보강, 에이전트에 스킬 등록(C05) |
| 스킬 결과 형식이 매번 다름 | 출력 형식이 고정되지 않음 | `SKILL.md`에 고정 출력 템플릿 명시 |
